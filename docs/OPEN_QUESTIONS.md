## 1. 优先解决的问题

| 问题 | 影响 | 推荐方案 | 验证与通过标准 |
| --- | --- | --- | --- |
| 数据源能否稳定访问 | 搜索、新闻页面、目录或 Token 权限变化会导致内容缺失 | 原生 RSS/Atom 和正式 API 优先；按来源适配、限流、缓存、隔离失败；可选 RSSHub 补源 | 在目标部署环境接通约 100 个仓库、3 个官方资讯源、1 个论文源及 Release；连续运行 48 小时，来源状态可追踪、无静默失败，单源失败不影响其他任务 |
| 历史数据与冷启动 | 第一天无法直接给出自采的完整周/月增长 | 立即保存快照，当前目录先可用；历史导入须核对来源与口径，数据不足显示观察中 | 缺端点不进正式榜；7/30 天净增长与双周期加速度分开标资格；不将当前总 Star 当作区间增长 |
| 发现覆盖与分类偏差 | 只跟随 Trending 会漏掉潜力项目，宽泛关键词会引入噪声 | Topics、关键词、种子、近期创建和成熟仓库并行发现；分片与分类配额；手工添加入口 | 建立人工标注的覆盖样本，含不同语言、年龄、Star 量级和 Agent 类型；报告漏检及误分类，不宣称覆盖全 GitHub |
| 潜力分是否有用 | 已拟定的权重未验证，可能偏爱小分母、营销爆发或资料丰富的项目 | 固定可解释规则起步，保留增长门槛；候选与算法版本化；提供观察入口和人工排除 | 与仅按净增长、仅按增长率的基线比较；按当时可用数据选 Top 20，后续观察 7/14 天的持续增长与维护，积累多个周期后再判断效果 |
| 资讯去重和时间是否正确 | 转载刷屏、旧闻变今日、不同模型版本误合并 | URL/GUID/arXiv/Release ID 条目去重，再按实体与版本聚合事件；发布时间与抓取时间分离 | 用约 50 条人工标注内容验证，覆盖转载、旧文、更新、未知时间和相似版本；记录合并错误，提供人工拆分/合并覆盖 |
| Skills/插件指标的粒度 | 仓库 Star 容易被误用为单体资源热度 | 仓库榜与资源目录分开；SKILL.md/manifest 保留路径证据；安装遥测单独存储 | 用至少 10 个含多资源的仓库验证识别；每个资源可打开源路径；缺安装量不伪造资源独立排行 |
| 中文摘要质量与成本 | 可能编造功能、遗漏限定条件，批量生成成本不确定 | 结构化输入、原文证据、SHA/hash 缓存、按需摘要与每日预算；无模型显示原文/模板 | 用约 30 个项目和 30 条资讯抽查事实、链接和语言；记录模型、用量与费用，再设默认预算；生成方式与失败降级可见 |
| 调度与持久化 | 本地电脑关机即中断；临时托管文件系统可能丢失数据库 | 首版单机持久卷、任务锁、可重入 CLI、过期状态和一致性备份；稳定运行后再扩容 | 在目标环境验证重启、断网、重复任务和恢复备份；恢复后历史与榜单可查，不误写零值 |

“48 小时”仅用于首轮运行验证，不能证明长期稳定；7/30 天增长和14/60 天双周期评分需要相应历史。当前 9—14 个工作日是实现估算，历史积累、外部源适配超预期和评分效果验证另计。

## 3. 三种落地组合

| 组合 | 组成 | 适用条件 | 本项目建议 |
| --- | --- | --- | --- |
| A：轻量独立实现 | 本项目采集器 + RSS/正式 API + 可选 RSSHub + SQLite | 以统一发现站为核心、初始来源数量有限 | 默认采用，控制服务数量，并把各来源适配器做成可替换模块 |
| B：接现成阅读后端 | Miniflux 或 FreshRSS + 本项目榜单/API/前端 | 已有大量订阅、成熟阅读状态和后台管理需求 | 留好适配层，实际源管理成本高时再采用 |
| C：先单独试用热点工具 | TrendRadar + 现有 GitHub 发现网站 | 优先快速验证资讯阅读与筛选习惯 | 可作为对照，不能直接替代用户所需的统一项目与资源排行产品 |

推荐 A。项目的主要自研价值是候选发现、真实历史快照、可解释潜力分、Agent 资源识别，以及资讯和项目的可靠关联；通用 feed 格式解析使用成熟依赖。

## 4. 尚未固定的产品选择

以下可以先采用默认值，不需要逐项阻塞开工：

- 周/月默认显示滚动 7/30 天；自然周和自然月刊后续补充，界面不混用称呼。
- 中文技术资讯优先，同时接入英文原始来源；普通营销、融资默认不进入重点流。
- 先做 Web、自托管与本地收藏；账号、公共注册、消息推送留待后续。
- 暂定 SQLite 单机；若确定多实例或多人协作写入，再选 PostgreSQL。
- 模型厂商可替换；真实摘要评估后确定性价比和预算，模型不可用时浏览流程仍正常。

真实持续运行前需要明确部署机器与网络条件，配置服务端 GitHub Token；启用 AI 中文摘要时再配置模型凭证与预算。当前不需要在聊天中提供凭证。

## 5. 推荐的下一步验证交付

当前已完成 100 个仓库的真实采集和第二阶段本地版本。下一步是在稳定运行环境持续观察 48 小时，并提高完整元数据比例；实现时间与观测时间分开记录，不能把当前结果视为已经完成长期验证。

PoC 交付包括：可手动执行的采集命令、真实样本数据库、来源可用性矩阵、失败和限流报告、分类/资源识别样本、资讯去重与摘要抽查报告。若未配置模型，摘要评估项标记“未验证”，不将模板效果替代模型评估。

PoC 不等待完整一个月历史即可进入 Web 开发；完整区间榜与潜力效果评估依赖持续积累。首版上线时对数据成熟度明确标记。
